# Frontend PROD.Guild / Let’s start here. — каждый файл простыми словами

Полный разбор 288 отслеживаемых файлов: React/TypeScript, конфигурация, API-контракты, тесты, имитация backend, CSS, изображения, шрифты и служебные workers. Снимок frontend: master, коммит dffd802 — Add ML case discovery to frontend. Документ подготовлен 18 октября 2026 года.

Для каждого файла указано, что он делает, зачем устроен именно так и какой у решения компромисс. Пути в каталоге относятся к корню frontend. Это объяснение реализации, а не построчный перевод синтаксиса и не заявление, что каждый сценарий уже проверен на работающем сайте.

## 1. Что это за проект

Frontend — всё, что человек видит и нажимает в браузере: главная, вход, каталог заданий, отправка решения, проверка чужой работы, профиль, чаты и уведомления. Здесь платформа называется Let’s start here.; её продуктовые сценарии относятся к PROD.Guild.

Здесь не обучается нейросеть и не хранится основная продуктовая база. Frontend показывает данные и отправляет действия основному серверу, то есть backend. Backend решает, что пользователь имеет право делать, сохраняет кейсы, решения и оценки, рассчитывает баланс и при необходимости вызывает отдельный ML-сервис.

На примере публикации: браузер собирает заголовок и условие, вызывает сервер создать/сохранить черновик, затем просит опубликовать конкретную версию. Он не превращает просто локальный объект в настоящую публикацию. На примере рекомендации: браузер получает готовые карточки от backend, а не держит служебный ключ ML и не обращается к Qdrant.

## 2. Короткий словарь

| Термин | Простое объяснение |
| --- | --- |
| React-компонент | Функция/класс, описывающая кусок интерфейса: кнопку, форму или страницу. |
| JSX / TSX | Способ писать похожую на HTML разметку внутри TypeScript-компонента. Это не отдельный HTML-файл на каждую страницу. |
| TypeScript | JavaScript с проверкой типов до запуска. Помогает обнаружить неверные поля, но не проверяет автоматически любой ответ сети. |
| Route / маршрут | Связь адреса вроде /student/ID с нужной страницей React. |
| Hook | Функция use..., которая связывает компонент с состоянием, эффектами, формой или запросами. |
| API-адаптер | Небольшой слой, знающий адрес запроса и поля backend и возвращающий удобные данные интерфейсу. |
| Query / mutation | Чтение серверных данных / действие, которое меняет данные. TanStack Query хранит результат и состояние ожидания/ошибки. |
| Кэш | Уже полученные данные в памяти браузера, которые можно показать и затем обновить. Это не основная серверная БД. |
| Инвалидация | Пометить сохранённые данные как требующие обновления, например после нового сообщения или сохранения профиля. |
| Mock / fixture | Имитация сервера либо заранее придуманные данные для разработки и тестов. Это не сведения реальных пользователей. |
| WebSocket | Открытое соединение для уведомлений о событиях без ручного постоянного обновления страницы. |
| Service worker | Отдельный браузерный обработчик для задач вроде перехвата dev-запросов или фонового push. Здесь это два разных worker. |

## 3. Что происходит при открытии сайта

```text
index.html
  → main.tsx
      → при необходимости дождаться MSW
      → общий QueryClient + BrowserRouter + AppErrorBoundary
      → App.tsx: выбрать маршрут, сессию и режим данных
          → публичная оболочка либо AppLayout участника
          → нужная feature-страница
              → API-адаптер → /api → backend
              → состояние → настольный/мобильный вид
```

Vite нужен для разработки и сборки. В dev он пересылает /api на нужный backend и поддерживает WebSocket upgrade, убирая префикс /api. В готовом Docker-образе Node уже не запускает Vite: Caddy раздаёт собранную папку dist.

React Router меняет страницу внутри приложения без скачивания отдельного HTML для каждого URL. Поэтому сервер статики должен при прямом открытии неизвестного файлового пути вернуть index.html. Именно для этого в Caddyfile есть try_files. Но этот файл не содержит backend-proxy: production /api должен направлять внешний reverse proxy из отдельной инфраструктуры.

## 4. Где находятся главные экраны и реальные действия

До входа корень / показывает landing. После входа тот же корень показывает рекомендации. /welcome оставляет возможность открыть приветствие и уже вошедшему человеку. /catalog — общий каталог, /cases/ID — кейс, /my-cases — свои задачи, /student — свои прохождения, /reviewer — очередь проверок, /profile — личный профиль.

Самые насыщенные реальные сценарии собраны в LiveWorkspacePages.tsx и LiveReviewerPages.tsx. Отдельные файлы без Live в той же workspace-папке в основном обслуживают fixture-режим: CatalogPage, StudentPage, ReviewerPage и другие используют MockWorkspaceContext. Называть их автоматически неиспользуемыми неправильно — они подключаются условно для тестов/дизайна. Но и считать их доказательством реальной записи на backend тоже нельзя.

Пример отправки решения:

1. По attemptId загружаются попытка и закреплённая версия условия, а не просто последняя версия кейса.
2. Пользователь вводит решение и выбирает допустимый режим проверки.
3. UI сохраняет идентификатор request_id вместе с содержимым этой попытки отправки.
4. Адаптер передаёт текст и request_id backend; интерфейс ждёт подтверждения.
5. При потере ответа текст остаётся. Явный повтор того же содержания может использовать тот же request_id, чтобы backend распознал повтор, а не создал дубль.
6. После успеха обновляются история и списки. Если закреплённое условие не открылось, история доступна, но отправка/проверка блокируется.

Это не универсальная гарантия для всех записей: например, startAttempt при каждом новом вызове сам генерирует request_id. Поведение каждой операции надо читать по её адаптеру и состоянию страницы.

## 5. Как frontend связан с уже разобранным ML

```text
Профиль: выбранные интересы и подтверждённые оценки
  → frontend: POST /api/recommendations с limit, без goal
  → backend: профиль + доступные кандидаты → внутренний ML
  → backend: готовые карточки и причины
  → frontend: показать в полученном порядке

Цель: «хочу научиться делать API на Python»
  → frontend: POST /api/recommendations с goal и limit
  → backend → текстовый ML-ранкер
  → backend → frontend
```

Сетевую часть здесь выполняет recommendationsApi.ts. На главной после входа LiveRecommendationsPage запрашивает три карточки без goal. В каталоге CatalogRecommendations.tsx добавляет режим «По моей цели» и поле до 2000 символов. Введённая цель сохраняется в URL и переносится через вход, включая Yandex-returnTo.

Если backend вернул mode=rules_fallback, интерфейс сообщает о резервной подборке. Он не запускает свою нейросеть взамен и не изображает локальные фикстуры настоящим ML. Коды причин преобразуются в подписи вроде «По твоим интересам» или «Поможет развить навык».

Карта навыков показывает средние оценки по зачтённым кейсам и число кейсов от backend. Это не score смыслового сходства и не результат выбора интереса кнопкой. В fixture-режиме похожий экран рассчитывается отдельной простой learningInsights-функцией; её нельзя выдавать за production-алгоритм ML.

## 6. Как устроены вход, профиль и мобильные виды

Основная схема, зафиксированная в AGENTS.md: API-адаптер → модель/общее состояние → page → отдельные desktop/mobile views. Она хорошо видна на auth, profile, chats и учебном demo. Страница создаёт одну форму выше ResponsiveView, а он монтирует ровно один внешний вид.

Почему не две постоянно смонтированные копии, одна скрытая CSS? У них могли бы быть отдельные эффекты, подписки и состояние ввода. Почему логика не внутри каждого вида? При смене ширины старый вид размонтируется и потеряет черновик. Общий state выше вида удерживает его. Условие мобильной ширины в useMobileView — до 639 px.

В текущих live-workspace-модулях подход реализован менее строго: запросы, mutations и большой JSX находятся вместе, а многие страницы адаптируются CSS. Поэтому нельзя утверждать, что у каждого экрана проекта уже есть отдельный завершённый мобильный компонент. Это разница между заявленным правилом и фактической степенью разделения.

Email-вход получает обычный accessToken и сохраняет его с userId в localStorage. Это позволяет пережить перезагрузку. При 401 защищённая feature завершает сессию; после выхода запросы отменяются, приватный кэш очищается. Наличие токена локально не доказывает его действительность: окончательный ответ даёт backend.

Yandex-кнопка не содержит client secret. Она создаёт временный случайный state, сохраняет контекст попытки и отправляет человека к провайдеру. Callback проверяет state и срок, убирает одноразовый code из адреса и отправляет code backend. Там происходит обмен, требующий секрета. Вход и регистрация имеют разные операции; неудачный вход не создаёт аккаунт автоматически.

## 7. Как устроены чаты и уведомления

Чаты отправляют сообщения по HTTP. WebSocket сообщает, что появился чат или сообщение. Клиент проверяет событие, помечает соответствующие запросы устаревшими и перечитывает HTTP-историю. Он не просто добавляет непроверенный socket-пакет в список.

Так повторное событие не создаёт вторую копию сообщения; обновление после reconnect помогает восстановить пропущенные изменения. История загружается по 30 сообщений с курсором «раньше этого message_id», затем объединяется и очищается от дублей. Сетевая ошибка отправки оставляет текст и не вызывает слепой автоматический повтор.

Уведомления внутри сайта имеют свою историю HTTP, обновление раз в 30 секунд и отдельный поток событий. В текущем коде notification-stream и chat-stream реализованы отдельно. Во время Chats могут существовать два подключения к /api/events; фразу «один socket у приложения на всё» фактический код не подтверждает.

Browser push — ещё один, необязательный канал. Он нужен, чтобы показать уведомление вне обычного React-экрана. Включается только после действия пользователя, разрешения браузера и конфигурации Firebase. public/firebase-messaging-sw.js показывает фоновые уведомления; public/mockServiceWorker.js перехватывает dev-HTTP. Совпадение слова worker не делает их одной функцией.

## 8. Три режима, которые легко перепутать

| Режим | Что на самом деле происходит | Что это позволяет проверить |
| --- | --- | --- |
| Обычный live | Страницы и адаптеры обращаются к backend через /api. При пустом каталоге показывается пустота. | Реальную интеграцию можно подтвердить только с работающим сервером и данными; по одному исходнику она не доказана. |
| MSW, VITE_API_MOCKING=true в dev | Браузерные HTTP-запросы перехватываются и получают вымышленные API-ответы из src/mocks. Настоящий Yandex и chat-WebSocket не запускаются. | Те же формы/адаптеры, ошибки, задержки, private-state, пагинацию. Не все бизнес-операции backend воспроизведены. |
| Workspace fixtures, VITE_WORKSPACE_MOCKING=true в dev либо test-mode | App подставляет отдельные workspace-экраны и MockWorkspaceProvider с локальным React-state. | Дизайн и согласованную цепочку «кейс → работа → ревью» без настоящего HTTP для этих действий. Это отдельная имитация, не MSW. |

Два dev-флага независимы. Для полного привычного демонстрационного сценария README предлагает включить оба. Один HTTP-mock-флаг не означает, что каждый live-workspace endpoint уже имеет обработчик. Неизвестные /api-маршруты в общей имитации получают явный missing-handler-ответ.

Есть и учебный модуль Examples в features/demo. Это показательный список/деталь/редактор с отдельным контрактом. Его маршруты доступны только в dev с API mocks, страница загружается лениво. Он не является четвёртым backend и не должен превращаться в обязательную продуктовую функцию.

## 9. Почему выбран такой подход, а не другой

Названия библиотек не доказывают, что они единственно возможны. React/TypeScript/Vite и остальные основные инструменты уже заданы шаблоном и AGENTS.md. Ниже — назначение конкретного решения и его цена, а не выдуманная история выбора авторов между всеми конкурентами.

| Решение | Зачем сделано здесь | Компромисс и возможный другой подход |
| --- | --- | --- |
| React и TypeScript | Повторяемые компоненты и ранняя проверка согласованности данных/свойств. | Нужна сборка и дисциплина состояния. TypeScript не валидирует настоящий JSON автоматически; для важных входов здесь отдельно применяется Zod. |
| Feature-папки | Связанный сценарий держит API, состояние, страницу и виды рядом. | Меньше поиска по всему проекту; при этом несколько live-файлов всё равно выросли в крупные модули с несколькими страницами. Это не полностью единообразная архитектура. |
| TanStack Query | Состояние загрузки, ошибки, кэш и обновление после действий решаются общим механизмом. | Требуется аккуратно выбирать ключи и очищать личные данные при выходе. Не каждый queryKey содержит userId, поэтому общая очистка сессии важна. |
| React Hook Form + Zod | Общая форма и явные правила ввода без двух независимых mobile/desktop-копий. | Не все live-формы переведены на эту схему: есть локальный useState/FormData. Нельзя описывать рекомендованный паттерн как уже повсеместно выполненный. |
| Генерация типов из OpenAPI | Одни имена полей и путей вместо ручного пересказа большого API. | Сгенерированные файлы велики, а устаревший контракт сгенерирует столь же устаревшие типы. Синхронизация с backend всё равно нужна. |
| Относительный /api | Одна клиентская сборка не содержит жёсткий адрес каждого backend-окружения. | В dev нужен Vite-proxy, в deployment — внешний proxy. Статический Caddy этого репозитория сам его не создаёт. |
| Отдельные mobile/desktop views | Разные композиции при одной форме и одном наборе запросов. | Дублируется часть разметки. Общая логика должна жить выше переключателя, иначе resize сбросит состояние. |
| HTTP как источник, WebSocket как сигнал | Историю можно перечитать, а повторное событие не дублирует записи. | На событие делается дополнительное чтение; задержка зависит от сети. Текущие разные потоки ещё не сведены к одному общему подключению. |
| Не повторять mutations автоматически | Потерянный ответ не доказывает, что сервер не выполнил действие. | Пользователю иногда нужен ручной повтор. В особо важных местах дополнительно сохраняется request_id, но не следует автоматически обещать такую гарантию всем операциям. |
| Локальная сессия | Вход переживает перезагрузку без нового client-side аккаунта на каждой странице. | Токен доступен JavaScript; это выбранная схема backend-контракта, а не HttpOnly-cookie. Один интерфейс не управляет всеми рисками и сроком серверного токена. |
| MSW и локальные fixtures | Можно делать UI, воспроизводить ошибки и писать тесты без сервисов. | Mock проще backend и может пропустить несовпадение реального контракта. На демоданных нельзя измерить качество ML или объявить реальную экономику защищённой. |
| Ленивый Matter.js и CSS-анимации | Физика загружается для видимой сцены, простые движения делает CSS, reduced motion сохраняет статичный вид. | Дополнительная библиотека и аккуратная очистка кадров/подписок. Декоративный эффект не должен стать условием доступности содержания. |
| Локальные картинки/шрифты | Изображения и типографика приходят вместе со статикой, маски можно перекрашивать темой. | Вес сборки и несколько шрифтов; происхождение и сопроводительные тексты ресурсов надо хранить отдельно. Генеративная модель при просмотре сайта не вызывается. |
| Docker builder → Caddy | Node собирает статические файлы, runtime отдаёт только результат. | Для изменения встраиваемых VITE-параметров нужна новая сборка. Один frontend-контейнер не является всей платформой. |

Далее каждый файл описан отдельно. Для изображений и лицензий объясняется назначение ресурса; для тестов — защищаемое поведение; для конфигурации — какая команда её использует. Не все 288 файлов являются запускаемыми скриптами.

## 10. Запуск, маршруты, HTTP, сессия и тема

Файлов в разделе: 19.

| Файл и роль | Что делает доступным языком | Почему так и какие есть ограничения |
| --- | --- | --- |
| `src/api/client.ts` — **Общий HTTP-клиент** | Фабрика типизированного openapi-fetch-клиента с базовым /api. Перед запросом читает актуальную сессию и добавляет Bearer-токен. В dev может искусственно задержать ответ для просмотра загрузки. | Один транспорт не даёт разным разделам забыть авторизацию или адрес API. Относительный адрес не привязывает сборку к одному серверу; перенаправление делает Vite либо внешний proxy. |
| `src/api/demo-schema.d.ts` — **Сгенерированные типы учебного API** | Аналогичный набор типов только для /demo/items из отдельного demo-контракта. | Учебные операции не должны выглядеть частью настоящего продуктового backend-контракта. Разделение позволяет удалить пример независимо от основного API. |
| `src/api/errors.ts` — **Общие ошибки запросов** | ApiError сохраняет HTTP-статус; остальные функции различают временный отказ, сеть, ограничение частоты и подбирают безопасные сообщения. | Одной строкой «ошибка» нельзя решить, нужно ли повторить запрос или войти заново. Централизация сообщений уменьшает разнобой и не заставляет интерфейс показывать пользователю необработанные подробности сервера. |

## 26. Что уже можно заключить и что не проверялось

По исходникам видно подключение настоящих API-клиентов и страниц для backend, включая /recommendations, кейсы, решения и ревью. Это больше, чем статичный макет. Но код клиента не доказывает, что доступен сервер, корректно настроены Yandex/Firebase, наполнен каталог и проходит весь пользовательский путь в production.

При этом разборе приложение не запускалось, npm-зависимости не устанавливались, unit/integration/e2e и сборка frontend не выполнялись. Проверены состав клона, исходный код, связи маршрутов/модулей и полнота объяснения файлов. Сгенерированный HTML проверен отдельно. Названия live-*.test означают тесты клиентского сценария с подставными API; это не фактическое взаимодействие с рабочим сервером.

Существенные особенности, которые не стоит потерять при пересказе:

1. README и docs/chats содержат исторические детали. Текущий socket-путь — /api/events, а не встречающийся в старой инструкции /api/chat/stream.
2. HomePage и MobileNavigation сохранены в коде, но нынешний App не использует их как основной Home/нижнюю навигацию. InkDrawing также не имеет найденных прямых импортов. Это не повод удалять файлы без отдельной задачи; это объяснение текущей связи.
3. В live-workspace есть крупные файлы с объединённой логикой и JSX. Правило разделять виды и state — целевой паттерн проекта, а не достоверное описание каждого существующего файла.
4. Экспертный раздел здесь реализует путь заявителя: список, вопрос, создание, просмотр готового ответа и отмену. Форм взятия вопроса и отправки экспертного ответа в прочитанном модуле нет. Администрирование также реализовано здесь прежде всего как справочник навыков, не полный набор модераторских действий.
5. Строковые поля *_md сейчас в основных прочитанных live-страницах выводятся как текст через JSX. Название поля Markdown не означает, что установлен полноценный Markdown-renderer или редактор.
6. История ученика/ревьюера сохраняется на экране при недоступном условии. README прямо отмечает известное расхождение backend со старой закреплённой версией; это не проверялось заново на сервере в рамках данного разбора.
7. Встроенная поддержка system-темы не полностью совпадает с восстановлением сохранённого значения: стартовое чтение ThemeProvider восстанавливает dark либо light. Обычный UI-переключатель здесь выбирает именно их.
8. GitHub Pages для этого документа публикует объяснение репозитория. Это не развёртывание самого React-приложения с его backend, ML и авторизацией.

## 27. Откуда взяты причины решений

Факты о поведении взяты из фактических импортов, маршрутов, запросов, форм и условий в src, а также Dockerfile, Caddyfile, Vite и package.json. Принятая структура разработки описана в AGENTS.md. Происхождение рисунков и шрифтов — в README внутри public и sources.json. Протоколы входа и чатов сопоставлены с текущими адаптерами и checked-in контрактами, а не только со старыми инструкциями.

Утверждения «общая форма удерживает ввод при смене вида», «HTTP-повтор может дублировать запись», «поздний ответ не должен восстанавливать личный кэш» подтверждаются и адресными тестами. Это объясняет, почему в hooks много проверок токена, refs и cleanup: они защищают конкретные сценарии, а не просто усложняют код.

Причины вроде «большой файл ускорил сборку связанного сценария, но усложнил сопровождение» являются технической интерпретацией видимого устройства. В репозитории нет документального сравнения React со всеми альтернативными фреймворками; здесь оно не приписывается авторам. Аналогично по одному CSS-файлу нельзя доказать, почему дизайнер предпочёл конкретный цвет или рисунок — можно показать способ реализации и его последствия.

## 28. Полнота и воспроизводимость

Список получен через git ls-files на master dffd802: 288 файлов, в том числе 169 в src, 40 в tests и 54 в public. Каждому отслеживаемому пути соответствует ровно одна строка разбора. Из 40 файлов tests три — helpers/setup, остальные 37 — файлы *.test.ts/tsx; это число файлов, не число реально выполненных тестовых случаев.

Служебная .git-папка не является частью этих 288 исходных файлов: Git создаёт её для истории, ссылок и настроек. node_modules и dist после клонирования не создавались этим разбором. Исходники frontend не редактировались, коммиты в GitLab и изменения серверного окружения не выполнялись.

Публикуемые index.html и Markdown содержат объяснение, а не полный исходный репозиторий, его картинки, node_modules или секретные настройки. Это самостоятельный документ по конкретному снимку кода.
